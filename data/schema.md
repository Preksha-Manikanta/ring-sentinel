# Ring Sentinel — Dataset Schema

The dataset is **synthetic but real** (deterministically generated, not hand-written
or randomly faked at runtime). It is the evaluation substrate for the whole
pipeline: `data → NetworkX graph → deterministic risk engine → API → UI`.

Generated by `data/generate_dataset.py` with a fixed seed, so every run produces
the identical dataset (required for reproducible scoring and holdout evaluation).

## `accounts.csv`

| column            | type   | notes                                                        |
|-------------------|--------|--------------------------------------------------------------|
| account_id        | str    | `acct_0001` … stable id                                      |
| created_at        | ISO ts | account creation timestamp                                   |
| device_id         | str    | shared-attribute candidate                                   |
| ip_address        | str    | shared-attribute candidate                                   |
| address           | str    | shared-attribute candidate                                   |
| card_fingerprint  | str    | shared-attribute candidate                                   |
| upi_id            | str    | shared-attribute candidate                                   |
| phone_number      | str    | shared-attribute candidate                                   |
| segment           | str    | `organic` / `family` / `office` / `ring`                     |
| true_ring_id      | str    | ground-truth label; empty for legitimate accounts           |

`true_ring_id` is **ground truth only** — the engine never reads it. It exists
solely so `eval/` can compute precision/recall.

## `orders.csv`

| column        | type   | notes                                                  |
|---------------|--------|--------------------------------------------------------|
| order_id      | str    | `ord_00001`                                            |
| account_id    | str    | FK → accounts                                          |
| created_at    | ISO ts | order timestamp                                        |
| amount        | float  | INR                                                    |
| promo_value   | float  | promo/discount value redeemed (0 if none)             |
| refund_value  | float  | refunded value (0 if none)                            |
| status        | str    | `captured` / `refunded` / `chargeback`                |
| channel       | str    | UPI / CARD / NETBANKING / WALLET                       |
| location      | str    | city                                                   |

## Ring embedding logic

- **6–8 seeded abuse rings**, 4–12 accounts each.
- Each ring shares **≥ 2 hidden attributes** drawn from
  {device_id, ip_address, address, card_fingerprint, upi_id, phone_number}.
- Rings exhibit behavioral signals: high order velocity, high promo redemption
  ratio, refund/chargeback concentration, and clustered creation timing.

## Legitimate look-alike traps (must NOT score high)

- **Family**: shares `address` only; distinct devices / cards / normal behavior.
- **Office**: shares `ip_address` only; otherwise independent and normal.
- **Single-attribute overlap**: incidental sharing of one device or one IP.

These exist to prove Ring Sentinel is not `shared identifier == fraud`.

## `holdout_labels.json`

20% of the seeded rings, held out untouched. Contains
`{ "holdout_ring_ids": [...], "account_true_ring": { account_id: ring_id } }`.
Weights/thresholds in `engine/config.py` are tuned only against the other 80%.
Final metrics are computed **only** on this holdout.
